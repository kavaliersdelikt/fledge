# Fledge 0.7.3.1 plan: "Aviary" (Plugins v2)

Status: **plan only, parked for a later release.** Renumbered after the limits update ([0.7.2.1 "Perch"](../releases/v0.7.2.1.md)) took the next slot; the hosting update ([0.7.1.1 "Rookery"](v0.7.1.1-rookery.md)) adds a narrow *payments provider* plugin contract, so parts of section 1 (host crypto, DELETE) land earlier. Baseline: panel 0.7.2.1 "Perch", plugin `apiVersion` 1.
Constraints for the implementation phase: **do not push, do not commit unless asked.** Finish with the release checklist (see the end): docs, landing page, README, release notes, version bump.

## Why

Plugins v1 (0.6.1.1) can do two things: provide a **catalog** (the Modrinth browsers) and receive **event hooks**. The docs say so honestly:

> Plugins cannot add pages or routes to the panel, define their own notification channels or call the panel's API. The interface covers catalogs and event hooks. Custom plugin UI is a candidate for a later release.

0.7.3.1 closes those three gaps without giving up what makes v1 safe: plugin code stays in the QuickJS sandbox, the plugin host still holds no credentials, and the panel renders everything itself.

## Goals

1. A plugin can **add pages** (admin pages, server tabs, dashboard cards) and **HTTP routes** (webhook receivers, status endpoints).
2. A plugin can **define notification channel types** (Telegram, ntfy, PagerDuty, SMS, ...) that people configure like the built-in ones.
3. A plugin can **call the panel's API** through a small, curated, permissioned interface, never the raw REST API.
4. Plugins can **run on a schedule** and react to **more events**, because 1 to 3 are of little use without triggers.
5. v1 plugins keep working unchanged. A plugin author can adopt one feature at a time.
6. Nothing a plugin does can break the panel's look, accessibility or security posture. Pages follow the Plumage theme automatically.

### Non-goals (stay on the "cannot do" list)

- **Arbitrary plugin JavaScript, HTML or CSS in the browser** (no iframes, no custom React). Pages are described as data and drawn by the panel. This is the main design decision; the reasons are in [Pages](#2-pages-and-routes).
- Plugins cannot read or change users, passwords, sessions, API tokens, settings, appearance or other plugins, and cannot delete servers or nodes.
- No per-customer plugin installs, no plugin marketplace payments, no hot-loaded native code.
- Changing the agent. No agent change is planned; the agent version only moves with the release number.

## 1. The foundation: a panel bridge and a better host

Everything else depends on two infrastructure pieces.

### 1.1 Per-call panel bridge

Today the host never calls the panel. `host.panel.*` needs a way back without giving the host credentials.

- When the API invokes the host it sends a **call token**: random, bound to `{pluginId, callId, actor, grants snapshot}`, valid until the call's deadline (at most 25 s), usable only against one internal endpoint.
- The host's `host.panel.*` operations post to `POST /internal/plugin-bridge` on the API with that token, **on the plugins network only**. The endpoint refuses anything without a live token and is not routed by the web proxy.
- The API executes the operation as a **plugin actor** (below), checks it against the plugin's granted permissions and scope, rate limits it, audits it, and returns JSON.
- The host still has no database access, no standing secret that works outside a running call, and the token dies with the call.

### 1.2 The plugin actor

Operations run as `plugin:<id>`, not as an administrator. Authorisation is the **intersection** of:

1. what the admin granted this plugin (permission and server scope), and
2. when a person triggered the call (a page action, a catalog request): what **that person** may do. A customer cannot use a plugin to do something they cannot do themselves.

Hooks, schedules and public routes have no person, so only (1) applies.

Every bridge call is audited with the plugin as actor (`plugin.panel.call` with operation, target and result), and shown in the plugin's **Activity** tab.

### 1.3 Host concurrency

The host runs calls in one process (documented limit). With pages, routes and schedules that stops being acceptable.

- A small **worker pool** (default 2 workers, `PLUGIN_HOST_WORKERS`, 1 to 8) instead of one event loop. Each worker owns one QuickJS runtime at a time; a hung or crashed worker is replaced.
- A **queue with priorities**: person-initiated (pages, actions, catalog) before hooks before schedules; depth limit with a clear "busy" answer.
- Per-plugin concurrency cap (2), so one noisy plugin cannot starve the rest.
- The existing limits stay (25 s, 64 MB, 40 requests, 2 MB result); `limits.md` gains a queue/worker section.

### 1.4 Safer, richer host API

Added to the sandbox `host` object (all deterministic or checked on the host side):

- `host.crypto`: `sha256(text)`, `hmacSha256(key, text)`, `randomBytes(n)` (to 64), `base64`/`hex` helpers, constant-time `equals`. Needed to verify webhook signatures.
- `host.time.now()`, `host.sleep(ms)` (at most 5 s, counted against the deadline).
- `host.fetch` methods: `PUT`, `PATCH`, `DELETE` added (same network rules); needed by several channel APIs.
- `host.panel.*`: see [section 3](#3-calling-the-panel).
- `host.result`: helpers for UI trees and route replies (`host.ui.*`, `host.reply.*`), purely convenience constructors for plain objects.

## 2. Pages and routes

### Decision: server-driven UI, not plugin-supplied browser code

Letting a plugin ship JavaScript or HTML into the panel's origin would let any community plugin read the session, call the full API as the logged-in admin and defeat the sandbox. It would also ignore the Plumage theme and the accessibility floors. An iframe from a separate origin avoids the first problem but needs a second hostname and breaks single-container installs.

So a page is **a JSON tree the plugin returns and the panel draws** with its own components. The plugin's code still runs only in the sandbox; the browser runs only Fledge's code. Themes, light/dark, density, text size, translations of labels the panel owns, keyboard support and contrast all come for free.

### 2.1 Manifest

```jsonc
"apiVersion": 2,
"pages": [
  { "id": "overview", "label": "Fleet health", "icon": "activity",
    "placement": "sidebar",            // sidebar | server-tab | dashboard-card
    "audience": "admin",               // admin | users (people who can see the server) | everyone
    "refreshSeconds": 30 }             // optional auto refresh, 10 to 3600, only while visible
],
"routes": [
  { "id": "alert-in", "method": "POST", "path": "alert", "access": "public",
    "maxBodyBytes": 65536, "description": "Receives alerts from the monitoring service" }
]
```

Permissions: `ui:pages` (needed for any page), `routes:public` (a route reachable without a session; the admin sees the full URL and must switch each public route on).

### 2.2 Page calls

- `fledgePlugin.page(pageId, ctx)` returns a UI tree. `ctx` has `{ user: { id, name, role }, server?, query, locale }`; no tokens, no cookies.
- `fledgePlugin.action(pageId, actionId, payload, ctx)` handles buttons and forms and returns `{ toast?, refresh?, tree? }`.
- Calls count towards a **page failure** counter separate from the auto-disable one: an erroring page shows an error card with the message and a "Copy details" button and never switches the plugin off by itself.

### 2.3 Component vocabulary (fixed, versioned, v2.0)

`stack`, `row`, `card`, `heading`, `text` (inline emphasis and links only), `stat`, `badge`, `alert` (info/warn/bad/ok), `keyvalue`, `table` (columns, rows, optional row actions, paging up to 200 rows), `list`, `progress`, `sparkline`/`bars` (small SVG drawn by the panel from a number array), `tabs`, `form` (the same field types as plugin settings: string, number, boolean, select, secret, plus `textarea`), `button` (action, confirm text, danger style), `link` (panel path or an approved host), `empty`, `code` (monospace block with copy).

Rules enforced by the panel, not the plugin: node count (at most 400) and depth (at most 8); text length caps; no HTML; links limited to `https://` on hosts the plugin declared in `network:` or to panel paths it may see; icons from the panel's icon set by name; every interactive element gets a label; destructive buttons need a `confirm`. An unknown component renders as a clear "needs a newer Fledge" placeholder so newer plugins degrade gracefully.

### 2.4 Placement

- **Sidebar**: a "Plugins" group (hidden when empty), respecting the Plumage label overrides for the group heading. Admin pages for admins; `users` pages are server tabs, never sidebar items.
- **Server tab**: appears on servers the viewer can open; the plugin gets `ctx.server` (id, name, template, node) and may only use `servers:*` bridge operations for that server (intersection rule above).
- **Dashboard card**: a small tree on the dashboard for admins.
- Routes: `/plugins/<id>/<page>` in the panel; the URL is stable and shareable to people who may see it. Server tabs: `/servers/<id>?tab=plugin:<id>:<page>`.

### 2.5 Routes (HTTP endpoints)

`ANY /api/x/<pluginId>/<path>` runs `fledgePlugin.route(routeId, request)` with `{ method, path, query, headers (allow-listed), body (text, bytes up to the route cap), ip }`.

- Access levels: `public`, `user` (a signed-in browser session), `admin`. Tokens are not accepted for `user`/`admin` routes in this release (same rule as Appearance writes).
- **Public routes are the sharp edge**, so: off by default per route; 64 KB body default, 256 KB maximum; per-route and per-IP rate limits (default 60 per minute); the plugin must verify the sender itself (the host provides `host.crypto.hmacSha256` and a per-route **signing secret** setting the panel can generate and show once); a failing public route is never counted towards auto-disable (an attacker could otherwise switch a plugin off).
- **Responses are constrained** so a plugin cannot serve a page from the panel's origin: status, a body of `application/json` or `text/plain` only, fixed headers (`nosniff`, `Content-Security-Policy: sandbox`, `Cache-Control: no-store`), up to 1 MB. No `Set-Cookie`, no redirects to other origins.
- CORS: none unless the route declares an allowed origin list (never `*` together with credentials).
- No WebSockets or streaming in this release.

## 3. Calling the panel

A curated API surface, each operation its own permission. Not a REST proxy.

### 3.1 Operations and permissions

| Permission | Operations in `host.panel` |
|---|---|
| `panel:servers.read` | `servers.list({ filter })`, `servers.get(id)` (state, template, node, resource use, ports, never environment secrets), `nodes.list()` |
| `panel:servers.power` | `servers.start(id)`, `stop(id)`, `restart(id)`, `kill(id)` |
| `panel:servers.console` | `servers.command(id, text)` (rate limited), `servers.consoleTail(id, lines)` |
| `panel:servers.files` | `files.list`, `files.read` (to 1 MB, text), `files.write` (to 1 MB), through the same path-safety code as the file manager |
| `panel:backups` | `backups.list(id)`, `backups.create(id)` |
| `panel:notify` | `notify({ kind, title, body, severity, serverId })`: emits a panel notification under the plugin's own event kind |
| `panel:audit.write` | `audit(action, detail)` under `plugin.<id>.*` |

Deliberately **not** offered: users, invitations, sessions, tokens, settings, appearance, other plugins, node enrolment, server create/delete/transfer, database credentials, environment secrets. These can be requested as candidates for a later release; each would need its own threat review.

### 3.2 Scope

Each of `panel:servers.*`, `panel:backups` has a **scope** chosen by the admin at install and shown in plain language: *all servers*, or *only these servers / this template*. The plugin cannot widen it; widening is a new approval. Scope is stored as `plugins.grants` (jsonb) beside `granted_permissions`.

### 3.3 Limits and loop protection

- At most **20 bridge calls per invocation** and **120 per minute per plugin** (configurable by an admin down, not up).
- A plugin-caused event carries `origin: plugin:<id>`; **a plugin is never invoked for events it caused**, and a chain depth of 3 stops runaway hook, action and hook loops. Counters are visible in Activity.
- Destructive operations (kill, file write, command) show up in the audit log with the page action or trigger that caused them.
- A plugin turned off stops being callable immediately (the token check re-reads the enabled state).

## 4. Notification channels

### 4.1 Manifest

```jsonc
"channels": [
  { "id": "telegram", "label": "Telegram", "description": "Send alerts to a chat",
    "settings": [
      { "key": "chatId", "label": "Chat ID", "type": "string", "required": true },
      { "key": "botToken", "label": "Bot token", "type": "secret", "required": true }
    ] }
]
```

Permission: `notifications:channel`. The `settings` schema reuses the existing field validator, including secrets (encrypted at rest, never returned).

### 4.2 Behaviour

- A channel type appears in **Settings, Notifications** (and the per-user channel form when the plugin allows it) next to Webhook, Discord, Slack and Email, with the plugin's icon. The form is generated from the schema.
- `notification_channels.kind` becomes `plugin:<pluginId>:<channelId>`; config and secret go in the existing `config`/`secret` columns. The existing event selection, server filter, dedupe, status and last-error display all keep working.
- Delivery calls `fledgePlugin.deliver(channelId, event, config)` in the host (event shape = today's webhook payload); the plugin returns `{ ok, message? }`. The existing delivery path records `last_status`/`last_error`, with an 8 s timeout and the usual retry rules.
- A **Send test** button calls `fledgePlugin.test(channelId, config)` if present, else sends a sample event.
- Disabling or removing the plugin parks its channels (shown as "plugin off", never deleted); reinstalling the plugin brings them back. Channel counts toward the existing 10-channel limit.
- Failed deliveries never count towards plugin auto-disable beyond the existing rule for sandbox errors, since a wrong chat id is not a broken plugin.

## 5. Schedules and more hooks

### Schedules

```jsonc
"schedules": [ { "id": "poll", "every": "5m", "description": "Check the monitoring service" } ]
```

Permission `schedule`. Minimum interval 1 minute, at most 4 per plugin, run as `schedule:<id>`, 25 s limit, overlapping runs skipped. Multi-replica safe through a Postgres advisory lock and a `plugin_schedule_state` row (`last_run`, `next_run`, `last_error`). Shown with next/last run in the plugin's Activity tab, with a **Run now** button.

### Hooks

Add the panel's existing notification events as hooks, `event:<kind>` (`server.crashed`, `backup.failed`, `node.offline`, ...), plus `server.started`, `server.stopped`, `backup.completed`, `user.created` (id only, no personal data). Payloads are documented per event. Hooks are best effort, 8 s, ignored result, as in v1.

## 6. Manifest, validation and compatibility

- `apiVersion` accepts 1 or 2. Features that need 2 (`pages`, `routes`, `channels`, `schedules`, the new permissions) are rejected in a v1 manifest with a clear message. Unknown future major versions are refused as today.
- New fixed permissions: `ui:pages`, `routes:public`, `panel:servers.read`, `panel:servers.power`, `panel:servers.console`, `panel:servers.files`, `panel:backups`, `panel:notify`, `panel:audit.write`, `notifications:channel`, `schedule`. Plain-language descriptions in the install prompt, with scope selectors where relevant and the dangerous ones (`power`, `console`, `files`, `routes:public`) marked.
- Limits: at most 8 pages, 8 routes, 4 channels, 4 schedules; manifest and package size limits unchanged (package 2 MB).
- Updates that add permissions, pages with wider audience, public routes or a wider scope need re-approval (existing mechanism, extended to scope and routes).
- `minPanelVersion` set to `0.7.3.1` on every v2 plugin.
- `pack.mjs` (the packaging tool) validates v2 manifests and ships a **UI preview**: a local command that renders a page tree to text for authors, plus a mock bridge for tests.

## 9. Security review (to be written into `plugins/security.md`)

Threats and the planned answer:

| Threat | Mitigation |
|---|---|
| Plugin steals the admin session or calls the full API | No plugin code in the browser. Bridge ops are a closed list. |
| Confused deputy: a customer drives an admin-scoped plugin | Intersection rule for person-initiated calls |
| Bridge token abuse by a compromised host | Token per call, bound to plugin, grants and deadline; endpoint only on the plugins network; rate limited |
| Stored XSS through page text, links or images | Data-only trees, text nodes only, link allow-list, no HTML, no images |
| Public route abuse (DoS, spoofed senders, switching a plugin off) | Per-route enable, size, rate and IP limits, signing secret helper, failures not counted |
| Loops (hook to action to hook) | Origin tagging, depth cap, per-minute caps |
| Starvation by a slow plugin | Worker pool, per-plugin concurrency, queue priorities |
| Secrets leakage into pages/logs | Secret settings never in `ctx`, redacted in logs, never in trees |
| Supply chain | Unchanged: signatures, checksums, tiers; new permissions re-prompt on update |
| Plugin-defined channels as SSRF | Delivery goes through the same host `network:` allow-list |

Honest limit to restate: the sandbox is defence in depth, and a plugin granted `panel:servers.files` or `panel:servers.power` for all servers can do real damage if it is malicious. The install prompt says so and defaults the scope to "pick servers".

## 11. Implementation phases

1. **Foundation:** manifest v2, grants with scope, host worker pool and queue, bridge with call tokens, plugin actor, audit, Activity log. (Largest and riskiest; ship nothing user-visible until it passes the bridge tests.)
2. **Host API:** crypto, time, sleep, fetch methods, `host.panel.*` read operations.
3. **Channels:** provider dispatch, forms from schema, test send, parking.
4. **Pages:** UI validator, renderer, sidebar/server tab/dashboard placements, actions.
5. **Routes and schedules:** public/user/admin routes with limits; scheduler with locks.
6. **Power operations:** power, console, files, backups with scopes (after the read path is proven).
7. **Bundled plugins, packaging tool (`pack.mjs` UI preview), install dialog scopes.**
8. **Hardening pass:** security review table walked line by line, hostile corpus, load test with 20 plugins, browser pass.
9. **Docs, landing, README, release notes, version bump** (below).

## 13. Open decisions

1. **Version name and number** (0.7.3.1 "Aviary" assumed).
2. **Raw API access:** this plan says no (curated operations only). If you want an `host.panel.request()` escape hatch for admins, it would need a per-route allow-list and is not included.
3. **Custom browser UI:** deferred, as above. The vocabulary is versioned so components can be added in point releases.
4. **User-level installs/channels by plugins** (customers adding a plugin channel for themselves): planned as allowed only when the plugin sets `allowUserChannels` and the admin enables it; otherwise admin-only. Confirm the default.
5. **Registry:** the signed registry format needs a `apiVersion` field so the store can hide plugins newer than the panel. Small change, included in phase 1.

## 14. Known limits to publish

- One bridge, one scope per permission; no per-user plugin permissions.
- Pages refresh by polling, not live push; no streaming routes.
- The UI vocabulary is intentionally small; a plugin that needs a custom widget cannot have it yet.
- English only; plugins supply their own text.
- Sandbox is not a hard boundary (restated).
