# Fledge 0.6.x plan: "Roost"

Status: **plan only, nothing implemented.** Baseline: `main` at 8edc3f7 (panel 0.5.2.x, agent 0.5.2.1).
Constraints for the implementation phase: **do not push or commit to the remote**. Finish with release notes, a version name, `.env.example`, and the README updated (see [Release checklist](#release-checklist)).

## Theme

0.5 made Fledge resilient (failover, disk limits, agent updates). 0.6 makes it **extensible and self-serve**: a plugin system with a built-in browser and one-click install, shipped with Modrinth mod and plugin browsers. Around that, the 0.6 line adds the features a panel needs once real people use it: automation, notifications, richer templates, quotas, and hardening.

## Release train

Fledge uses four-part versions (`0.5.1.1`, `0.5.2.1`). Proposed:

| Version | Name | Contents |
|---|---|---|
| **0.6.1.1** | Roost: foundations | Plugin runtime, store, permissions, agent `file.fetch` job, add-on-aware templates |
| **0.6.2.1** | Roost: Modrinth | Catalog browser UI, **Modrinth Mod Browser**, **Modrinth Plugin Browser**, add-on tracking, updates, rollback |
| **0.6.3.1** | Autopilot | Schedules v2, crash policy, notification center |
| **0.6.4.1** | Fit & finish | Template v2, customer quotas, extra ports, clone server, email invites and reset |
| **0.6.5.1** | Hardening | Passkeys, sessions UI, metrics history, OpenAPI, e2e tests, signed releases |

If you would rather ship one big release, 0.6.1.1 to 0.6.2.1 is the minimum coherent unit (the plugin system is not useful without a plugin). Everything after is independent and can be reordered.

## 1. Plugin system (0.6.1.1)

### Goals
- A plugin can be found, installed, configured and enabled **from the panel in one flow**, with no shell access and no `.env` edits.
- Plugins cannot silently take over the panel: they declare permissions, the admin approves them, and the runtime enforces them.
- Plugins contribute through **contracts the panel renders itself** (catalog providers, settings forms, server tabs, hooks). Most plugins ship no UI code at all.

### Plugin kinds and trust tiers
| Tier | Source | Runs | Notes |
|---|---|---|---|
| **Bundled** | `plugins/` in this repo, built into the image | In the plugin host | Maintained with Fledge; the two Modrinth plugins live here |
| **Verified** | Official registry, ed25519-signed index, SHA-256 per artifact | In the plugin host | One-click from the store |
| **Community / sideloaded** | URL or `.fledgeplugin` upload | In the plugin host | Needs an explicit "I trust this code" admin opt-in; shown with a warning badge |

Honest limit to document: Node isolation is defense in depth, not a hard security boundary. The README's trust model for plugins should say so.

### Package format
`.fledgeplugin` is a zip containing:
```
fledge-plugin.json     manifest
dist/index.js          server entry (single bundled ESM file)
icon.svg, README.md, CHANGELOG.md, LICENSE
```
Manifest sketch:
```jsonc
{
  "id": "modrinth-mods", "name": "Modrinth Mod Browser", "version": "1.0.0",
  "apiVersion": 1,                       // plugin API contract; panel refuses unknown majors
  "minPanelVersion": "0.6.1.1", "minAgentVersion": "0.6.1.1",
  "license": "AGPL-3.0-only", "author": "...", "homepage": "...",
  "permissions": [
    "network:api.modrinth.com", "network:cdn.modrinth.com",
    "servers:files.write", "servers:read", "storage"
  ],
  "settings": { /* JSON-schema subset, rendered by the panel; "secret": true fields are encrypted */ },
  "contributes": {
    "catalog": [{ "id": "mods", "label": "Mods", "appliesTo": { "addon": "mod" } }],
    "serverTab": { "label": "Mods", "when": "catalog:mods" },
    "hooks": ["server.created", "server.deleted", "server.variablesChanged"]
  }
}
```

### Runtime architecture
- New Compose service **`plugins`** (plugin host): a small Node process, no database credentials, no Docker socket, own network. Talks to the API over an internal authenticated JSON RPC. This follows the existing `updater` service pattern.
- Plugins get a **host object**, not ambient authority. Every call is checked against the manifest permissions:
  - `http.fetch(url)`: only to declared hosts, HTTPS only, no private/loopback/link-local IPs (SSRF guard, re-resolved after redirects), response size and time limits, honest `User-Agent: Fledge/<version> (<repo URL>)`.
  - `storage.get/set`: plugin-private KV in PostgreSQL (`plugin_kv`), size quota.
  - `settings`: the plugin's own validated settings; secrets decrypted only for the plugin.
  - `servers.*`: runs **as the acting user** through the existing `serverAccess` checks, never as a superuser. Plugins cannot touch servers the user cannot.
  - `log`: structured, per-plugin, visible in the UI.
- Node's `--permission` flag restricts the host's filesystem; a worker thread per plugin with memory limit and call timeouts; crash-looping plugins are auto-disabled with an audit event.
- Client side: panel-rendered contributions only in 0.6. A sandboxed-iframe bridge for custom plugin UI is explicitly **deferred to 0.7** (large attack surface).

### Data model (`db/schema.sql`, additive only)
- `plugins(id text PK, version, source, tier, manifest jsonb, enabled bool, installed_by, installed_at, updated_at, granted_permissions text[], artifact_sha256)`
- `plugin_settings` via the existing `settings` table (key `plugin:<id>`, secrets encrypted with the current mechanism)
- `plugin_kv(plugin_id, key, value jsonb, PRIMARY KEY(plugin_id,key))`
- `plugin_logs(id bigserial, plugin_id, level, message, at)` with retention pruning
- `plugin_registry_cache` for the signed index and ETags
- Audit events: `plugin.install`, `plugin.update`, `plugin.enable`, `plugin.disable`, `plugin.uninstall`, `plugin.permission.grant`

### One-click install and configure flow
1. **Plugins** page (admin): tabs *Store*, *Installed*, *Settings*. The store reuses the same catalog-browser component as Modrinth (see section 2), so it is dogfooded.
2. Click **Install**: dialog shows publisher, tier, version, changelog and **requested permissions in plain language** ("Download files from api.modrinth.com", "Write files to servers you choose"). Admin confirms.
3. API downloads the artifact, verifies SHA-256 and signature, unpacks into a versioned directory on a `plugins` volume, validates the manifest, and registers it.
4. **Configure wizard** is generated from `settings`: typed fields, defaults, live validation, a **Test** button that calls the plugin's optional `healthCheck()`.
5. **Enable** hot-loads the plugin in the host (no panel restart). Contributions (server tabs, store entries) appear immediately.
6. Update: store shows *Update available*; updates re-prompt only if permissions **grew**. Rollback keeps the previous version directory.
7. Uninstall: disables, stops, deletes artifact, optionally keeps or wipes plugin data. Add-ons that a plugin previously installed to servers are **left in place** and remain listed as "orphaned".

### API surface
`GET /api/plugins`, `GET /api/plugins/store`, `POST /api/plugins` (install), `PATCH /api/plugins/:id` (enable/disable/settings), `POST /api/plugins/:id/update`, `DELETE /api/plugins/:id`, `GET /api/plugins/:id/logs`, `POST /api/plugins/:id/health`. Plugin-contributed routes live under `/api/plugins/:id/x/*`, proxied to the host and authenticated by the panel. New API-token scope `plugins`.

### Agent work (prerequisite for add-ons)
- New job kinds: **`file.fetch`** (agent downloads a URL itself, outbound, streaming to disk with size cap, host allowlist from the job payload, **SHA-256/SHA-512 verification**, atomic rename into the server data dir, path-traversal checks reusing `files.go` logic) and **`file.delete`** (batch).
- Why agent-side download: no large files through the API, works with disk-limit volumes, reuses existing path-safety code.
- `minAgentVersion` gate: the UI explains and offers *Update agents* when a node's agent is too old.
- Agent version bumps with the release; Go tests for fetch (checksum mismatch, oversize, redirect to disallowed host, traversal).

### Testing
- Contract tests for host permission enforcement (denied host, private IP, oversize, timeout).
- Manifest validation fuzz cases; signature tamper test; install/update/rollback/uninstall integration test against the disposable-PostgreSQL harness.
- Add `test:plugins` to `api/package.json` and CI.

## 2. Built-in catalog browser (0.6.2.1)

A generic panel component driven by a plugin's `catalog` contract, so any future provider (Hangar, CurseForge, Spiget, GitHub releases, a template catalog) gets a full UI for free.

**Provider contract** (implemented by plugins):
```
search({ query, filters, sort, page })     -> { items, total, facets }
project(id)                                -> { description (sanitized), gallery, links, license, ... }
versions(id, { target })                   -> versions compatible with the target server
resolve(versionId, { target })             -> { files:[{url, filename, sha256|sha512, size}], dependencies:[...] }
```
**UI**: search bar, facet filters (categories, loader, side), sort, infinite grid/list, detail drawer (rendered markdown through a sanitizer, gallery, links, license), **version picker preselected to the server's compatible version**, dependency review step, installed-state badges, keyboard navigation, mobile layout, Ctrl K integration ("Install mod...").

**Install pipeline** (panel API, shared by all providers):
1. Resolve target from the server: template add-on capability, `TYPE`, `VERSION`, loader.
2. Provider `resolve()`, then **dependency resolution**: required dependencies are auto-selected and shown; incompatible ones block with an explanation; optional ones are offered; already-installed ones are skipped.
3. Create `server_addons` rows (state `pending`), enqueue `file.fetch` jobs with hashes into the correct directory (`mods/` or `plugins/`).
4. Optional **safety backup** first (on nodes with volumes this does not stop the game).
5. Mark installed, prompt for restart ("Restart now / later"). Failures roll back partial files.

**Data model**: `server_addons(id, server_id, plugin_id, provider, project_id, version_id, version_label, filename, sha, installed_by, installed_at, source_url, state, auto_update bool, pinned bool)`; `plugin_catalog_cache` (query results with TTL and ETag so Modrinth's rate limit is respected).

**Template hooks**: templates get an **`addons` capability** descriptor so the panel knows what a server supports, derived from the template and variables instead of hard-coded:
```
{ "kind": "mod",    "dir": "mods",    "typeVar": "TYPE", "versionVar": "VERSION", "loaders": {"FABRIC":["fabric"], "QUILT":["quilt","fabric"], "FORGE":["forge"], "NEOFORGE":["neoforge"]} }
{ "kind": "plugin", "dir": "plugins", "typeVar": "TYPE", "versionVar": "VERSION", "loaders": {"PAPER":["paper","spigot","bukkit"], "PURPUR":["purpur","paper","spigot","bukkit"], "FOLIA":["folia"], "SPIGOT":["spigot","bukkit"]} }
```
(Existing templates `minecraft-paper`, `-purpur`, `-folia`, `-spigot`, `-forge`, `-neoforge`, `-fabric` are updated by an additive migration; add a Quilt template.) Custom templates can opt in via the template editor.

**Server "Add-ons" tab** (visible only when an enabled provider applies): *Browse*, *Installed* (enable/disable by renaming to `.jar.disabled`, remove, pin), *Updates* (check all, update one or all, with changelog and compatibility check), *Orphaned/unmanaged files* detected by scanning the directory.

## 3. The two bundled plugins (0.6.2.1)

Both live in `plugins/modrinth-mods` and `plugins/modrinth-plugins` and share `plugins/_shared/modrinth-client.ts`. Two separate plugins (not one with a switch) so an admin can run only the one they want, and permissions/settings stay tight.

### Modrinth Mod Browser (`modrinth-mods`)
- **Applies to**: Minecraft templates with the `mod` add-on capability (Fabric, Quilt, Forge, NeoForge, later any mod-loader template).
- Queries the Modrinth v2 API (`/search`, `/project/{id}`, `/project/{id}/version`, `/version_files/update` for batch update checks) with `project_type:mod`, `categories:<loader>`, `versions:<mc version>` facets and `server_side != unsupported` by default (toggle to show client-only mods).
- Picks the newest version matching `loaders` and `game_versions`, prefers `release` over `beta`/`alpha` (setting).
- Uses the version file `hashes.sha512` for verification; downloads only from `cdn.modrinth.com`.
- Dependencies from `dependencies[]` (`required`/`optional`/`incompatible`/`embedded`) feed the resolver. Shows a clear warning that most mods need matching client mods and which are server-side only.
- Settings: user-agent contact string, release channel, show client-only, results per page, optional install-time backup.

### Modrinth Plugin Browser (`modrinth-plugins`)
- **Applies to**: templates with the `plugin` add-on capability (Paper, Purpur, Folia, Spigot; Velocity/BungeeCord when templates exist).
- Same client with `project_type:plugin`, loader category per server software (Folia servers only see Folia-compatible plugins; Paper-compatible plugins are offered on Purpur).
- Same hash verification, dependency resolution (plugin dependencies such as Vault or ProtocolLib resolved when Modrinth lists them), update checks, enable/disable by renaming.
- Settings: contact string, release channel, preferred loaders order, backup before change.

### Shared behaviour and guardrails
- Respect Modrinth's rate limit: server-side cache, request coalescing, `User-Agent` set per their policy, backoff on 429, never called from the browser directly.
- Network permissions limited to `api.modrinth.com` and `cdn.modrinth.com`.
- Honest limits to document: only projects Modrinth hosts; unlisted/hidden projects excluded; jar-only (no `.mrpack` modpacks in this release); a restart is needed to load changes; the panel does not scan jars for malware, it verifies integrity against Modrinth's hash only.

### Stretch (only if time allows)
- **Modrinth Modpack Installer** as a third bundled plugin: install `.mrpack` server packs by file download or by using itzg's native `MODRINTH_MODPACK` env, with version pinning and updates.
- **Minecraft Manager** plugin: `server.properties` form editor, whitelist/ops/ban list editing, online players via RCON (RCON is already preset).

## 4. Autopilot (0.6.3.1)

Today `schedules` supports only `backup`/`command` on a fixed interval.
- **Schedules v2**: cron expressions with timezone, actions `power` (start, stop, restart), `command`, `backup`, `webhook`, and **task chains** with delays (e.g. broadcast "restart in 5 min", wait, save-all, restart). Per-run history with result. Missed-run policy (skip or run once).
- **Crash policy per server**: auto-restart on unexpected exit with backoff, crash-loop detection (N in M minutes then stop and notify), exit code and last log lines recorded as an event on the server page.
- **Notification center** replacing the failover-only webhook: events (server crashed, crash loop, disk over X %, memory pressure, backup failed or verification failed, node offline/online, failover, agent update failed, plugin crashed, update available), channels (webhook for Slack/Discord/Mattermost, generic JSON, SMTP email once 0.6.4.1 lands), per-user subscriptions and per-server rules, test button, in-panel inbox with unread count. Existing failover webhook is migrated, not broken.
- Plugin hook: plugins can register notification channels (later).

## 5. Fit and finish (0.6.4.1)

- **Template v2**: typed variables (string, number with range, boolean, select, regex-validated, secret), description and help text, per-variable *user can view/edit* flags, a **Startup** panel on the server page, template **import/export as JSON**, template versioning with "update servers to new template version" preview, Pterodactyl import keeps working. Replaces the flat `editable_variables text[]` by an additive migration that reads the old column.
- **Customer quotas**: per-customer limits (servers, total memory/CPU/disk, backups), enforced at create and resize, shown on the customer page. This is the first step toward hosting-provider use.
- **Extra ports**: add or remove additional allocations per server (query/RCON/voice ports), port range suggestion, conflict explanation, the `allocations` table already supports it.
- **Clone server**: create a new server from an existing one's newest backup (reuses restore + placement), with new name and ports.
- **Email**: SMTP settings with test button, invitations for new customers, password reset by email, collaborator invites. Recovery codes remain.
- Console: command history, saved quick commands, per-template console presets.

## 6. Hardening (0.6.5.1)

Addresses the "no production security review" caveat in the README. This does not claim a review happened; it reduces risk and gives reviewers material.
- **Passkeys (WebAuthn)** as a second factor option; **session management** UI (list, revoke, last-seen IP); optional admin IP allowlist.
- **Audit log** filters and export (CSV/JSON); retention setting.
- **Metrics history**: per-server CPU/memory/disk retained for 24 h to 30 d with downsampling (currently only live samples), charts on the server page, a few more Prometheus series.
- **OpenAPI 3.1 spec** generated from routes, served at `/api/openapi.json`, and API-token scope documentation.
- **CI**: Playwright end-to-end (login with 2FA, create server against a simulated node, install a Modrinth add-on with a mocked Modrinth), `npm audit`/`govulncheck`, SBOM, **signed release artifacts** and signed plugin registry key rotation procedure, CSP headers review.
- **Docs**: plugin author guide (`docs/plugins/`), host API reference, store submission rules, threat model.

## Cross-cutting rules for implementation

- **Migrations are additive** in `db/schema.sql` (existing style: `IF NOT EXISTS`, `ON CONFLICT DO NOTHING`). No destructive changes; the updater cannot reverse migrations.
- **Updater compatibility**: a new `plugins` service and volume must be handled by `compose.yaml`, `install.sh/ps1`, `update.sh/ps1` and the in-panel updater (`updater/server.mjs`), which rebuilds only API and web today.
- **Older agents**: feature-gate everything that needs `file.fetch`; clear error and one-click agent update.
- **Security checks on every new route**: `admin()`/`serverAccess()`, token `scope()`, request limits, SSRF guard on all outbound fetches, audit event for each mutation.
- **UI**: follow existing components (`DataTable`, `shared.tsx`, Ctrl K palette), motion respects reduce-motion, works on phones.
- **Tests**: each release adds API tests, Go tests where the agent changes, and extends `tests/` smoke scripts. CI additions listed per section.

## Risks and open decisions

1. **Plugin trust model**: confirm Bundled + Verified + Community tiers with an explicit admin opt-in for unsigned code. A hard sandbox (separate containers per plugin) is possible later but heavy.
2. **Registry hosting**: signed index in a separate GitHub repo (`kavaliersdelikt/fledge-plugins`) is assumed; needs a signing key held by you.
3. **Modrinth terms**: API use requires a descriptive `User-Agent`, and downloads must stay attributed and follow the API's rate limits; review current terms before release.
4. **Version naming**: the plan uses four-part numbers and one codename ("Roost") for the whole 0.6 line; the release notes can use a different codename per point release if preferred.
5. **Scope**: sections 4 to 6 are large. They are ordered so each release is shippable alone; cut from the bottom if needed.
6. **Version drift to fix first**: `.env.example` says `APP_VERSION=0.5.2.3`, `compose.yaml` defaults to `0.5.2.1`, the agent reports `0.5.2.1`, and `api/package.json` says `0.1.7`. Settle on one source of truth at the start of 0.6.1.1.

3. Write `docs/releases/v<version>.md` in the existing format (Highlights, Added, Changed, Fixed, Verified, Known limits, Upgrading).

5. Run the checks from the README's Development checks (API, web, agent) plus the new plugin tests.
6. Give you the release notes in chat and stop; no `git push`.
