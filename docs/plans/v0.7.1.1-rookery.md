# Fledge 0.7.1.1 plan: "Rookery" (the hosting update)

Status: **plan only, nothing implemented.** Baseline: panel 0.6.2.1 "Plumage", agent 0.6.2.1.
Constraints for the implementation phase: **do not push, do not commit unless asked.** Finish with the release checklist (see the end): tests, docs, landing page, README, release notes, version bump, codename.

A rookery is the colony where many birds nest and raise their young: a place that hosts others. That is what this release turns Fledge into.

## Theme

Until now Fledge is a panel an operator runs for people they invite. 0.7.1.1 makes it a panel a **hosting business** can run: strangers can sign up, buy a server, pay for it every month or year, and manage it, with the operator staying in control of limits, abuse, money and email.

| # | Pillar | One line |
|---|---|---|
| 1 | **Self-registration** | Sign-up with email verification, abuse controls, approval and invite-only modes |
| 2 | **Self-service servers** | Customers create (and delete) their own servers within what they are allowed |
| 3 | **Limits v2** | A layered, explainable limits system that can be switched off or set to warn only |
| 4 | **Plans and subscriptions** | Plans, prices, trials, a subscription engine with dunning, suspension and retention |
| 5 | **Store** | Customers buy admin-defined preset servers, monthly, quarterly, half-yearly or yearly |
| 6 | **Payments** | A provider contract for plugins, plus a bundled **Stripe** plugin (Checkout and Customer Portal) |
| 7 | **Email v2** | Editable templates, a reliable outbox with retries, receipts, dunning and security notices |

Everything is **off by default**. An existing panel behaves exactly as before after the upgrade (the default-look guarantee of 0.6.2.1 extends to behaviour: see [Upgrade safety](#upgrade-safety)).

## Reliability principles (apply to every pillar)

These are the rules the implementation is held to. Each has a test in the plan.

1. **The provider is the source of truth for money; the database is the source of truth for entitlement.** A webhook is only a *nudge*: on every relevant event we fetch the object's current state from the provider and apply that, so out-of-order, duplicated and replayed events cannot corrupt state.
2. **Exactly-once effects from at-least-once delivery.** Every webhook is stored first (unique `(provider, event_id)`), acknowledged, then processed by a worker with retries. Every side effect (create server, send mail, suspend) has an idempotency key or a unique constraint.
3. **The client never sends a price.** The browser sends a plan id and an interval. Amount, currency and trial come from the database at checkout time and are frozen on the order.
4. **No data loss by billing.** Billing suspends; it does not delete, unless the operator explicitly enabled auto-termination, and then only after a retention period and a final backup attempt. Lowering a limit never deletes anything either.
5. **Every state change is an audited, locked, monotonic transition.** One Postgres advisory lock per subscription, a `version` column, and a transition table that rejects illegal moves.
6. **Time comes from the database**, not from the app host or the browser. Timers are driven by a scheduler row, not by the process staying up.
7. **Fail closed for entitlement, fail open for the existing panel.** If billing is broken, new purchases pause and a banner tells the operator; running servers keep running and the rest of the panel is unaffected.
8. **Money is integers** (minor units, ISO 4217), never floats. Amounts are `bigint` with `CHECK (amount >= 0)`.
9. **Test mode and live mode never mix.** Every billing record carries `livemode`; the panel refuses to attach a live key to a database that holds test records and vice versa (explicit reset needed).
10. **Everything is explainable.** For any customer the panel can say why a limit is what it is, why a server is suspended, and which event caused a state.

## 1. Self-registration

### Behaviour

Settings, **Sign-up** (administrators). Off by default.

| Option | Values |
|---|---|
| Mode | `off`, `open` (anyone, email verified), `approval` (verified, then an admin approves), `invite` (registration only with an invite link or code) |
| Verify email | always on when mail is configured; sign-up cannot be turned on without working email (readiness check) |
| Allowed / blocked domains | optional lists; a small bundled disposable-domain list that can be switched off |
| Bot protection | none, or **Cloudflare Turnstile** / **hCaptcha** (site key + secret key; verified server-side through the guarded HTTP client) |
| Terms | optional terms and privacy URLs; acceptance is recorded (version, time, hashed IP) |
| Default plan | none (the customer gets nothing until they buy or are granted something), or a named free plan |
| Welcome email | on/off, editable (pillar 7) |

### Flow

1. `POST /api/auth/register` `{email, password, acceptTerms, captcha?}` creates a user in state `pending_verification` with `role='customer'` (never anything else; the role is not client-controlled).
2. A verification email with a single-use token (hashed in `user_tokens`, kind `verify`, 24 h). The response is **identical** whether or not the address exists; for an existing address the mail says "you already have an account" with a sign-in/reset link (no enumeration).
3. `POST /api/auth/verify` consumes the token: state becomes `active` (open mode) or `pending_approval` (approval mode); an admin notification is raised for approvals.
4. Until `active`, the user cannot sign in to anything but the "check your email / resend" screen, owns nothing and can create nothing.

### Abuse controls (all on by default when sign-up is on)

- Rate limits using the existing `request_limits` table: per IP (5 registrations per hour), per email (3 per day), per IP for resends (5 per hour) and a global ceiling (default 200 per hour; trips a banner and pauses sign-up if exceeded, since it signals an attack).
- Honeypot field and a minimum form-time check on the panel form (cheap, silent).
- Password: existing 12+ rule, plus rejection of the 1,000 most common passwords (bundled list).
- Unverified accounts are deleted after 7 days (scheduler job).
- Admin tools: approve/reject, block an email or domain, resend verification, mark verified, delete unverified.
- Everything is audited (`signup.*`).

### Account lifecycle additions

- **Email change** with verification of the new address and a notice to the old one.
- **Account deletion** (customer self-service): blocked while a subscription is active (cancel first) or while servers exist unless the customer confirms deleting them; after a 14-day grace period (configurable) the account is anonymised (email replaced, name cleared, sessions and tokens removed); invoices are retained in anonymised form for the legal retention period.
- **Data export** (JSON: account, servers, subscriptions, invoices metadata) for the customer.
- New users columns: `email_verified_at`, `status` (`active`, `pending_verification`, `pending_approval`, `deletion_pending`), `signup_source`, `terms_version`, `terms_accepted_at`, `deletion_at`. The existing `disabled` flag keeps meaning "blocked by an admin".

## 2. Self-service servers

### Modes (Settings, Customers)

| Mode | Customer can |
|---|---|
| `off` (default, current behaviour) | nothing; admins create servers |
| `presets` | create from admin-defined **presets** only (the same objects the store sells, price 0 or already paid) |
| `custom` | choose a template and resources freely **within their effective limits** |

Also: *allow customers to delete their own servers* (default off), *require a backup before deletion when storage is on* (default on), *deletion cooling-off* (a deleted server is hidden and recoverable for N hours; default 24, 0 = immediate).

### Implementation

- Refactor the body of `POST /api/servers` into one function `provisionServer(input, actor)` used by the admin route, the self-service route, and subscription fulfilment. Same placement code (capacity, free ports, disk free), same transaction, same audit entry; no behavioural change for admins.
- New `POST /api/me/servers` `{presetId | {templateId, memoryMb, cpuPercent, diskMb}, name, location?, variables?}`. The owner is always the caller. Editable variables only (existing template rule). The image allow-list and template visibility rules still apply.
- Customers see only templates the admin marks **customer-visible** (new `templates.customer_visible`, default false so nothing leaks on upgrade) and only locations allowed by their limits.
- The new customer delete path reuses the deletion job and the existing "deleting" state.
- Placement failure returns a clear message ("No capacity for this location right now"), never raw node data (today's admin response lists rejection reasons per node; customers get a sanitised version).
- `servers.created_via` (`admin`, `self`, `store`) and `servers.subscription_id` (nullable, unique) are new.
- Rate limit: 10 server creations per customer per hour; the limits system caps the rest.

## 3. Limits v2

### What exists today (per-customer quotas)

Six per-customer numbers in `users.quota` (servers, memory, CPU, disk, backups, extra ports), enforced in a few code paths, no way to switch them off, no defaults, no per-server maxima, no explanation.

### The model

A **limit set** is a small object. Each field is one of: a number, `null` (explicitly unlimited) or *absent* (inherit from the layer below).

```
servers, runningServers,
memoryMb, cpuPercent, diskMb,                         // totals across the customer's servers
maxServerMemoryMb, maxServerCpuPercent, maxServerDiskMb,   // per server
backups, backupsPerServer, backupStorageMb,
extraPorts, collaboratorsPerServer, schedulesPerServer,
allowedTemplates[], allowedLocations[],
flags: selfCreate, selfDelete, sftp, addons, extraPortsAllowed, schedulesAllowed
```

**Layers, lowest to highest precedence**

1. **Defaults for customers** (Settings, Limits). Starts as "nothing set", i.e. today's behaviour.
2. **Plan allowances**: the sum for additive fields (servers, totals, backups, ports) and the most permissive for maxima, lists and flags, over the customer's active *account* plans (pillar 4).
3. **Customer override** (the existing `users.quota`, same meaning, now shown as "override"). An explicit value, including unlimited, always wins; an admin who types it means it.

An *effective limits* resolver returns, per field, `{value, source}` so the UI can say "memory: 16 GB (Plan: Creator)" or "servers: unlimited (override)". The resolver is a pure function with a table-driven test matrix.

**Plan-backed servers** (created by a *server plan*, pillar 4) are governed by their plan and are **excluded from quota usage**; otherwise buying "Minecraft 4 GB" would eat the customer's own allowance and block the next purchase. They still count toward node capacity like any server and toward `runningServers` only if the admin sets that option.

### Global controls (Settings, Limits)

| Control | Meaning |
|---|---|
| **Enable limits** | Master switch. **Default on** so an upgrade does not silently remove limits an operator already relies on. When off, nothing is enforced anywhere (stored values are kept). |
| **Mode** | `enforce` (block with a clear message), `warn` (allow, but notify the customer and the admins, audit `limit.exceeded`), `off` (same as master switch, for symmetry in the UI) |
| **Apply to admins** | Default off. Admin actions can also use the existing `force`. |
| **Allow per-customer overrides** | Default on; off hides the override editor |
| **When a limit is lowered below usage** | Existing servers stay; new creations are blocked; the customer sees "over limit" |
| **Warn at** | Percent (default 80) at which the customer is notified once per window |
| **Show usage to customers** | Default on |

### Enforcement points

One function `checkLimits(ownerId, action, delta, {db, force})` replaces direct quota calls and is called transactionally (owner row `FOR UPDATE`, the existing pattern) from: server create (admin, self, store), resize, clone, restore into a new server, backup create, extra ports, collaborator add, schedule create, add-on install (when `addons` is limited), transfers. A test greps the API for server-mutating routes and fails when one does not go through `checkLimits` (so a future route cannot forget it).

### UI

- Admin: Settings → Limits (global), Customer page → **Limits** tab (override editor with the effective view and sources, usage bars, "reset to inherited").
- Customer: **Usage** card on the overview (bars with the numbers and the source of each limit; hidden by the setting).

### Compatibility

`users.quota` is untouched and becomes the override layer. A panel with quotas set before the upgrade enforces exactly the same after it.

## 4. Plans and subscriptions

### Concepts

- A **Plan** is something that can be given or sold. Two kinds:
  - **Server plan**: a *preset* (template, resources, location pool, variables, extra ports). Each subscription provisions **exactly one server** and its lifecycle follows the subscription. This is the classic hosting product ("Minecraft 4 GB").
  - **Account plan**: an *allowance* (a limit set added to the customer's effective limits). The customer spends it themselves ("Creator: 5 servers, 16 GB").
- A plan has **prices**: one per billing interval (month, 3 months, 6 months, year), each with amount, currency, optional trial days and optional setup fee (one-time, shown clearly).
- A **Subscription** links one customer to one plan and one price, and (for server plans) to one server.

### Plan fields

`name`, `slug`, `description` (plain text, a few lines), `features[]` (bullet strings), `kind`, `visibility` (`public`, `hidden` reachable by link, `private` grant-only), `sortOrder`, `active`, `stock` (max concurrent subscriptions, null = unlimited), `perCustomerMax` (default 5 for server plans, 1 for account plans), `limits` (account plans) or `preset` (server plans), `prices[]`, `trialOncePerCustomer`, `cancelBehaviour` (see below), `retentionDays` (override of the global retention).

Archiving a plan hides it from the store and keeps existing subscriptions running. A plan with subscriptions cannot be deleted.

### Price changes

Prices are immutable once a subscription exists on them. Editing a price creates a new price row; existing subscriptions keep the old one (grandfathering) unless the admin runs **migrate subscribers** (with preview of count and revenue change, applied at the next renewal, with a notice email). This avoids surprise charges.

### State machine

```
            checkout started
   (order) ───────────────► incomplete ──paid──► active ◄──────────┐
                                │                  │  ▲           │ pay (any time)
                          expired/failed           │  │ paid      │
                                ▼          trial   │  │           │
                             canceled   trialing ──┘  │           │
                                              payment failed       │
                                                  ▼               │
                                              past_due ──grace over──► suspended ──retention over (opt-in)──► terminated
                                                  │                        │
                                                  └── cancel ──► canceled ◄┘ (period end / immediate)
```

- Allowed transitions live in one table in code and are the only way state changes; illegal moves are logged and ignored.
- Each transition writes a `subscription_events` row (from, to, reason, source: webhook/scheduler/admin/customer, provider event id).
- Server effects of a transition:
  - `active`/`trialing`: server running (provisioned if not yet).
  - `past_due`: nothing yet; customer emailed (dunning).
  - `suspended`: server stopped and suspended with `suspended_reason='billing'`.
  - `active` again after payment: only a `billing` suspension is lifted; an admin or abuse suspension is never lifted by a payment.
  - `canceled` (end of paid period): server stopped and suspended (`billing`), data kept for the retention period.
  - `terminated`: only when **auto-terminate** is enabled (default off): final backup attempted, then the normal deletion job.
- **Dunning schedule** (Settings, Billing; defaults): payment failed day 0 email; day 3 reminder; **suspend at day 7**; day 14 final warning; **terminate at day 30 if enabled**. Evaluated by the scheduler against `past_due_since`, so a restart or a missed webhook cannot skip a step.
- **Cancel**: customer cancels at period end by default (access until then); admin can cancel immediately, with or without refund. Re-subscribe within retention restores the same server rather than creating a new one.
- **Upgrade / downgrade** (same kind): upgrade applies at once with provider proration and resizes the server (cpu/memory take effect on the recreate that the existing resize path performs; a restart is announced to the customer); downgrade applies at the next renewal and is refused if the new disk is smaller than the used disk. Switching between different templates is cancel + new.
- **Trials**: a price may have trial days; once per customer per plan; a card is collected up front (Checkout default) so a trial converts without a second step; "trial ending" email 3 days before.
- **Manual / complimentary subscriptions**: admin can grant any plan to any customer with provider `manual`, optional end date, optional note; no payment, same lifecycle (expiry reminders). Essential for staff, partners and migrations.
- **Orders**: every checkout attempt is an `orders` row (plan, price snapshot, owner, status `created → pending → paid | expired | failed`, provider session id, chosen server name/location/variables, terms version). Orders expire after 24 h. An order is what the payment is matched to; the browser return URL is *not* trusted for fulfilment.

### Fulfilment (the critical path)

1. Customer starts checkout. Server-side we check: store enabled, plan active and visible to them, interval offered, stock, per-customer max, limits (e.g. `selfCreate`), email verified, **capacity** (a dry-run of the placement for the preset; if there is no room the store says "temporarily sold out" and the order is not created), rate limit (5 checkouts per hour).
2. The order is stored with a frozen price snapshot; the provider plugin creates a hosted Checkout session using that snapshot and an idempotency key (the order id).
3. Provider webhook arrives (or the return page polls): the event is stored, then processed; the worker fetches the subscription state from the provider, matches the order, locks the subscription, and performs **idempotent fulfilment**: create the subscription row, provision the server (unique `servers.subscription_id`), mark the order paid, send the receipt and "your server is ready" emails.
4. If provisioning fails after payment (no capacity any more, node offline): the subscription is `active` with `fulfilment='failed'`, the customer sees "We're setting this up", the scheduler retries with backoff for 24 h, admins are notified, and a one-click **refund and cancel** (via the provider contract) is offered. The customer is never left without feedback and never charged twice.
5. The browser lands on a "Thanks" page that polls the order until the server exists (or shows the pending state); it never marks anything paid itself.

### Reconciliation

A scheduler job (every 15 minutes, advisory-locked) compares each non-final subscription with the provider (`reconcile` in the contract), repairs drift (a missed webhook), and records what it fixed. A "Billing health" panel lists drift, failed events, failed fulfilments and webhook age.

### Data model (additive)

`plans`, `plan_prices`, `subscriptions`, `subscription_events`, `orders`, `invoices` (mirror: number, status, amounts, currency, period, hosted URL, PDF URL, provider id), `billing_customers` (user, provider, provider customer id, livemode), `billing_events` (webhook inbox: provider, event id, type, payload, received, processed, attempts, error), `templates.customer_visible`, `servers.subscription_id`, `servers.suspended_reason`, `servers.created_via`.

## 5. The store

Off by default. A new **Store** section for customers (label renameable in Appearance, styled by the Plumage tokens).

### Admin

- **Readiness checklist** before it can be enabled: a payment provider plugin installed and its *Test connection* green; email configured; at least one active plan; terms and privacy URLs set; webhook endpoint reachable (a test event round trip); a company identity (name, address, support email) for receipts and the footer.
- Settings, Store: enabled, public catalog (browsable without sign-in; checkout needs an account), currency display, tax mode (see below), terms and privacy URLs, withdrawal notice text (digital-service wording for EU consumers, editable), support email, "sold out" behaviour, show prices incl. tax.
- A **Plans** admin page: create/edit/duplicate/archive, prices per interval, stock, preview of the store card, subscriber counts, MRR figure.
- **Subscriptions** admin page: filter by state/plan/customer, open one to see the timeline, invoices, server, dunning state; actions: cancel (now/period end), grant, extend, refund (via provider), retry fulfilment, suspend/unsuspend billing hold.
- **Invoices** page: mirror of provider invoices with links; export CSV.
- **Revenue overview**: MRR, active subscriptions, trials, churn this month, failed payments, simple (no accounting claims).

### Customer

- **Store**: plan cards with price toggle (monthly/yearly with "save X%" computed from the prices), features, stock state. Selecting a plan opens a review step: server name, location (if the plan allows a choice), allowed variables, price summary, trial notice, the terms checkbox and the withdrawal notice, then "Continue to payment".
- **Billing** page: subscriptions (state, next renewal, price), invoices, payment method and invoice details via the provider's customer portal, cancel / resume, change plan, "this server is suspended because payment failed" with a pay button.
- Server detail shows the plan, the renewal date and a billing warning when relevant.
- All pages work in light/dark/custom themes, have no layout shift, and respect text size and density.

### Tax and legal (stated plainly)

Tax is not computed by Fledge. The Stripe plugin can switch on **Stripe Tax** (automatic tax, billing address collection, tax ID collection) when the operator has it set up; otherwise prices are as entered. Invoices are the provider's hosted invoices. The docs say clearly that the operator is responsible for tax, consumer-law and invoicing compliance; Fledge provides the hooks, not legal advice.

## 6. Payments: the provider contract and the Stripe plugin

### Why a contract, not full Plugins v2

The parked Plugins v2 plan (pages, routes, panel API) is larger and not needed for payments. Payments need exactly three things the sandbox lacks: an inbound **webhook** with signature verification, **crypto helpers**, and a way for the core to **ask the plugin to talk to a provider**. So 0.7.1.1 adds one narrow contract, in the spirit of `catalogs` in v1:

```jsonc
"apiVersion": 1,                       // unchanged: payments is an additive contract
"permissions": ["network:api.stripe.com", "payments"],
"payments": { "id": "stripe", "label": "Stripe", "intervals": ["month","year"],
              "currencies": ["eur","usd","gbp","..."], "features": ["checkout","portal","refund","trial","tax","coupons"] }
```

New permission `payments` (plain-language prompt: "Take payments and manage subscriptions through this provider. It will see order and customer email details."). At most one active payment provider at a time in this release.

### Methods the plugin implements (all run in the sandbox)

| Method | Input (from core) | Returns |
|---|---|---|
| `healthCheck()` | n/a | `{ok, message, livemode, account}` (verifies the key and mode) |
| `createCheckout(order)` | frozen snapshot: order id, customer email/provider customer id, plan name, interval, amount, currency, trial days, setup fee, success/cancel URLs built by the core, metadata `{orderId}` | `{url, providerSessionId, providerCustomerId?}` |
| `createPortal(customer, returnUrl)` | | `{url}` |
| `reconcile(refs)` | provider subscription/invoice ids | authoritative normalised state: `{subscription:{id,status,currentPeriodEnd,cancelAtPeriodEnd,trialEnd,priceId,amount,currency}, latestInvoice:{...}}` |
| `webhook(request)` | raw body (string), allow-listed headers | `{ok, events:[{id, type, refs}]}`: the plugin **verifies the signature** (HMAC-SHA256, timestamp tolerance 5 min) and returns normalised, de-secreted event stubs; the core never trusts payload amounts |
| `changePlan(sub, newSnapshot, timing)` | | `{ok, effectiveAt}` |
| `cancel(sub, when)` | `when`: `period_end` or `now` | `{ok}` |
| `refund(invoiceRef, amount?)` | | `{ok, refundId}` |

The core owns everything else: orders, state machine, entitlement, provisioning, dunning, emails, UI. A provider plugin only translates. This keeps a second provider (PayPal, Mollie) a plugin-sized job later.

### Host additions (small, reviewed)

- `host.crypto`: `hmacSha256(key, text)`, `sha256(text)`, `timingSafeEqual(a, b)`, `randomHex(n)`.
- `host.fetch` allows `DELETE` (Stripe cancels with it) and form-encoded `POST` bodies (just a string; no change).
- A per-call **idempotency** helper is unnecessary: the plugin passes `Idempotency-Key` as a normal header.

### Core endpoints

- `POST /api/billing/webhooks/:provider`: **public**, no cookie auth, no CORS; raw body captured (Fastify content-type parser for this route only), 512 KB cap, per-IP rate limit, responds 2xx after the event is durably inserted. Rejects with 400 when the plugin reports a bad signature. Not covered by the web proxy's cookie logic.
- Customer (browser session only, never API tokens): `GET /api/store`, `POST /api/store/checkout`, `GET /api/store/orders/:id`, `GET /api/billing`, `POST /api/billing/portal`, `POST /api/billing/subscriptions/:id/cancel|resume|change`, `GET /api/billing/invoices`.
- Admin: plans CRUD, subscriptions list/detail/actions, invoices, health, provider status, test event.

### The Stripe plugin (bundled)

- Settings: mode (test/live, read from the key prefix and checked against `healthCheck`), **secret or restricted key** (secret field), **webhook signing secret** (secret field), automatic tax, collect billing address, allow promotion codes, statement descriptor suffix, API version pin.
- It uses **Checkout Sessions** in subscription mode with inline `price_data` (so no products or prices need syncing and nothing can drift), `client_reference_id` = order id, `subscription_data.metadata` carrying order and plan ids, the **Customer Portal** for payment methods/invoices/cancel, and `subscriptions` update/cancel for plan changes.
- Subscribed events: `checkout.session.completed`, `customer.subscription.created|updated|deleted|trial_will_end`, `invoice.paid`, `invoice.payment_failed`, `invoice.upcoming`, `charge.refunded`, `charge.dispute.created|closed`. Each is turned into a nudge; state is then fetched.
- Docs give the minimal **restricted-key permissions** list and a copy-paste `stripe listen --forward-to` line for local testing (`http://localhost:4000/api/billing/webhooks/stripe`). Key and secret entry happens in the panel UI by the operator only.
- Disputes: a dispute opens a billing hold on the subscription (server suspended, `billing`) and notifies admins; the outcome event releases or terminates per the operator's setting.

### Security specific to payments

- Cards never touch Fledge: hosted Checkout and Customer Portal only. PCI scope stays at the provider.
- Redirect URLs are built from `WEB_ORIGIN`, never from client input (no open redirect).
- Webhook: signature verified in the plugin, constant-time compare, 5-minute tolerance, replay blocked by the unique event id, body size cap, rate limit, no secrets in logs.
- Secrets: key and signing secret use the existing encrypted `secret` setting type; they are never returned by any API or put in logs, and plugin logs redact `sk_`, `rk_`, `whsec_` patterns.
- A compromised plugin sandbox can read its key: documented honestly; the bundled tier, the restricted-key guidance and the network allow-list (`api.stripe.com` only) are the mitigations.
- Checkout and portal creation are rate limited per user; failures are generic to the customer and detailed in the admin log.

## 7. Email v2

### Today

One synchronous `sendMail` with a text body; failures bubble to the request; four kinds of mail (invite, reset, test, notification).

### Plan

- **Templates for every transactional email**, editable in Settings, Email: *verify address, welcome, invitation, password reset, email changed (to old and new), password changed notice, two-step turned off notice, account deletion scheduled/completed, order received, receipt (payment succeeded), payment failed (dunning 1/2/3), server suspended for billing, server ready, subscription canceled, renewal upcoming, trial ending, plan changed, refund issued, limit nearly reached, limit reached, admin: approval needed, admin: fulfilment failed, admin: dispute opened*.
- Each template: subject, text body, HTML body (a clean generated layout from the Plumage identity: name, logo if reachable, accent; plain fallback), enabled toggle where it makes sense (security and billing-critical mails cannot be disabled), preview, **send test to me**, reset to default, and a variable list per template.
- **Safe templating**: `{{name}}`-style substitution only, HTML-escaped by default, no loops or code, unknown variables flagged on save, length caps, links limited to the panel origin, and a lint that rejects templates referencing variables a template does not provide. The renderer is a pure function with tests (including hostile input in names and server names).
- **Outbox**: `email_outbox` table. Sending enqueues; a worker (advisory lock, `FOR UPDATE SKIP LOCKED`) delivers with exponential backoff (1 min to 6 h, 8 attempts), per-recipient and global throttles, dedupe keys (so a replayed webhook does not send two receipts), and statuses `queued / sending / sent / failed`. Critical interactive mails (verification, reset) try inline first and fall back to the outbox so the user sees "sent" or a clear failure.
- **Delivery log** in the panel (who, which template, status, error, attempts), 30-day retention, with resend for failed items. Bodies are not stored beyond the rendering variables.
- **Sender identity**: company name, postal address and support email in the footer of billing mails (legal need in many countries); `Reply-To`; optional admin BCC for receipts.
- **Admin notification emails** for approvals, failed fulfilment, disputes, billing health.
- SMTP stays the transport (test connection already exists). Provider APIs (SES, Resend) and DKIM signing are not part of this release.

## Upgrade safety

- Every new feature is off by default; the default state reproduces 0.6.2.1 behaviour.
- `limits.enabled` defaults **on** with an empty default layer, so existing customer quotas keep enforcing identically.
- `templates.customer_visible` defaults false; no template becomes visible to customers by upgrading.
- All schema changes use `IF NOT EXISTS` / additive columns with defaults; rerunning the schema is a no-op.
- API: existing routes unchanged. New routes are namespaced (`/api/store`, `/api/billing`, `/api/me/servers`, `/api/auth/register|verify`).
- Rolling back to 0.6.2.1 leaves extra tables unused and harmless.

## Security review table (to be written into the docs)

| Threat | Mitigation |
|---|---|
| Mass registration / spam / email bombing | Verification, rate limits (IP, email, global), honeypot, optional captcha, domain lists, unverified cleanup, sign-up auto-pause on flood |
| Account enumeration | Identical responses; existing-account mail instead of an error |
| Price or plan tampering | Client sends ids only; amounts frozen server-side; order snapshot |
| IDOR on orders, invoices, subscriptions, servers | Owner checks in every query (`WHERE owner_id = actor`), tested with two customers |
| Forged or replayed webhooks | Signature in the plugin, timestamp tolerance, unique event id, state fetched from the provider |
| Webhook flood / DoS | Body cap, per-IP rate limit, store-then-ack, bounded worker |
| Double fulfilment / double charge | Unique constraints, idempotency keys, advisory locks, order state machine |
| Open redirect after checkout | URLs built from `WEB_ORIGIN` only |
| Free-tier and trial abuse | Default plan none, trial once per customer, per-customer plan max, server-creation rate limits, limits system, admin approval mode |
| Card testing via checkout | Hosted Checkout (provider Radar), per-user checkout rate limit, email verification required |
| Billing used to unsuspend an abusive server | `suspended_reason`: payment only lifts `billing` holds |
| Data loss through billing | Suspend, never delete by default; retention; final backup; opt-in termination |
| Secret leakage | Encrypted settings, never returned, log redaction, plugin sandbox, restricted-key guidance |
| Test/live confusion | `livemode` on every record, guard on key switch, loud test-mode badge |
| Privilege escalation via sign-up | Role fixed server-side to `customer`; no client-controlled role or owner |
| XSS / injection in emails and plan text | Escape by default, no HTML from admins in plans, templated variables only |
| Email as an attack vector (header injection) | Subjects stripped of newlines (existing), recipients validated, templates cannot set headers |
| Compromised payment plugin | Bundled tier, single allowed host, narrow contract (it never gets database or panel access), core validates every return |

## Not in this release (stated honestly)

- Tax calculation or compliance beyond switching on Stripe Tax; legal documents; accounting exports beyond CSV.
- Providers other than Stripe (the contract allows them); more than one active provider; PayPal/crypto.
- Usage-based billing, prepaid credit/wallet, hourly billing, add-ons purchasable on top of a plan (extra RAM/ports), reseller or affiliate programs, coupon engine of our own (Stripe promotion codes are passed through).
- Per-customer custom pricing; invoicing in more than one currency per customer.
- Fraud scoring beyond rate limits, verification and the provider's own tools.
- SES/Resend APIs and DKIM for email; translations of templates (English only; the structure allows languages later).
- Plugins v2 (pages, routes, panel API) stays parked in [v0.7.2.1-plugins-v2.md](v0.7.2.1-plugins-v2.md).
