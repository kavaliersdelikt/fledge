# Fledge API + node agent (beta implementation)

This is a single-process TypeScript/Fastify control plane with PostgreSQL persistence and a polling, outbound-only Go Docker agent. It is **not** a completed commercial release. Do not put paying customers on it without the missing hardening and real-node tests below.

## Run

Requires Node.js 20+, PostgreSQL 15+ (database/user allowed to create tables), and a 32-byte randomly generated encryption key. From `api/` on a normal POSIX filesystem:

```sh
npm ci
export DATABASE_URL='postgres://navrylo:YOUR_PASSWORD@localhost:5432/navrylo'
export ENCRYPTION_KEY="$(openssl rand -hex 32)" # persist in a secret manager; never regenerate after 2FA enrollment
export WEB_ORIGIN='http://localhost:3000'
export PORT=4000
npm start
```

`src/index.ts` applies the idempotent `../db/schema.sql` at startup. **Back up PostgreSQL before upgrades**; this is a simple additive schema, not a full versioned migration framework. Use TLS at the reverse proxy and set `NODE_ENV=production` for Secure cookies. Reverse proxy API/Web under the same site; cookies are `HttpOnly`, `SameSite=Strict`. Set `TRUST_PROXY=true` only behind a trusted proxy. CORS admits only `WEB_ORIGIN`. Browser calls use `credentials: 'include'`.

Required environment: `DATABASE_URL`, `ENCRYPTION_KEY` (64 hex characters), `WEB_ORIGIN` (defaults to `http://localhost:3000`), optional `HOST` (`0.0.0.0`), `PORT` (`4000`), `NODE_ENV`, `TRUST_PROXY`. For backups: `S3_BUCKET`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, optional `S3_REGION` (`us-east-1`) and `S3_ENDPOINT` (path-style S3). The endpoint in presigned URLs **must resolve and be reachable from every node agent and customers' browsers**; a Docker-only `minio` hostname or `localhost` on the control plane will not work on remote nodes. Use TLS for S3 outside private test networks. Without S3 configuration, backup, restore and backup schedules return 503; other features still work. `ALLOWED_IMAGE_PREFIXES` is a comma-separated prefix list, default `itzg/minecraft-server:,ghcr.io/lloesche/valheim-server:`. Configure the *same* list on each node agent; add trusted custom-image prefixes explicitly.

First-time `POST /api/auth/bootstrap` with `{email,password}` (12+ characters) creates the first provider admin only when no admin exists. The first-admin page then requires TOTP enrollment before normal use. The TOTP secret is AES-256-GCM encrypted with `ENCRYPTION_KEY` at rest. Once TOTP is enabled, the panel posts credentials with `stepwise:true`, receives a short-lived challenge, and completes sign-in through `POST /api/auth/challenge` with `{challenge,totp}`. The legacy inline-TOTP login remains supported. Do not expose bootstrap publicly before provisioning the first admin. `/api/auth/me` returns `{id,email,role,has2fa}`. Shared PostgreSQL-backed fixed-window limits cover login and selected sensitive operations; deploy an edge rate limit too.

Install one agent per Linux Docker node; see `../agent/README.md`. Register node with POST `/api/nodes`, request POST `/api/nodes/:id/enrollment`, then provide its 10-minute one-time token to the agent. Rotation invalidates the old credential immediately. Agents make outbound HTTPS requests, never accept incoming control-plane connections. Node status becomes disconnected after 35 seconds without heartbeat, while existing Docker containers continue independently.

## HTTP semantics

All routes are under `/api`. Except `/api/health`, `/api/auth/bootstrap`, `/api/auth/login`, and `/api/agent/*`, routes require a session cookie or narrowly allowlisted bearer token. Errors are `{error,message}` with HTTP 400/401/403/404/409/413/502/503/504. Lists are arrays, with `limit` (1–100, default 50) and `offset` on customers, servers, jobs and activity. Dates are UTC ISO strings. JSON uses camelCase for UI payloads; job/schedule/audit rows retain some SQL snake_case fields where documented by actual response. The browser live console and node agent use authenticated WebSockets: browsers connect to `/api/servers/:id/live` using a SameSite session cookie and Origin check; agents initiate outbound `/api/agent/stream` connections with node-scoped credentials. The control plane is a single-process relay; reconnect/backoff and node disconnect states are surfaced to the panel. Jobs remain pollable.

### Servers

`POST /servers` is admin only: `{name,ownerId,templateId,location?,nodeId?,memoryMb?,cpuPercent?,diskMb?,port?}`. It serializes candidate-node capacity reservations with PostgreSQL row locks, checks RAM headroom, configured CPU/disk reservation, last reported actual free disk, and TCP/UDP allocation uniqueness. Omit `nodeId` for automatic placement and `port` for auto-assignment in 20000–50000. Returns server, `{job:{id,state}}`, and `placement` with selected node and rejected-node reasons. Requested capacity is *reserved* until deletion completes. Docker enforces RAM/CPU/PIDs, but **diskMb is an admission reservation, not a filesystem quota**. A failed create retains its reservation until operator deletes/retries it.

`GET /servers`, `GET /servers/:id` list/get owned or shared servers. Any nonempty recognized collaborator grant (`view`, `console`, `files`, `backups`, or `manage`) allows list/detail metadata; an empty grant allows neither. **This does not confer other operations**: console/files/backups still require their corresponding grant, and `manage` implies all permissions. The detail response includes `effectivePermissions` (array of `view`, `console`, `files`, `backups`, `manage` grants; all five for browser-session admin/owner/manage collaborator, `view` only for a read-scoped API token), so clients can hide unauthorized controls. `status:'unreachable'` indicates node disconnection regardless of last observed container state; `observedStatus` preserves the last observation. The detail response includes startup `variables` only for a browser-session admin, owner, or manage collaborator; API tokens cannot read these secret values. Template startup and env values are similarly redacted from API-token reads. `PATCH /servers/:id` is admin-only for name, memory, CPU, disk and variables; changing RAM/CPU queues `configure` (Docker update), changing variables recreates the container with the same local data (downtime). Node/port/owner/template changes are rejected. `PATCH /servers/:id/settings` allows owner or manage collaborator to set `{variables:{KEY:'value'}}` **only for editableVariables declared by the template**; this recreates the container and returns `{jobId,state}`. `DELETE /servers/:id?confirm=true` (or JSON `{confirm:true}`) is admin-only and asynchronous. It is rejected with 503 while the node is disconnected so the server is not left in a misleading deleting state; otherwise the API creates a delete job and the UI waits for that job's success/failure before leaving the detail page. On success the agent removes local data and releases ports/reservations. While deletion is pending, new server actions/configuration/file operations/backups are rejected; queued work is failed on successful deletion, and the agent refuses stale jobs for deleted servers.

`POST /servers/:id/actions` with `{action}` queues start/stop/restart/kill (owner/manage); admin-only suspend/unsuspend/reinstall. Reinstall requires `{action:'reinstall',confirm:true}` and erases local files. Backup and restore actions are described below. `suspend` prevents customer start until unsuspended. All long operations return `{jobId,state:'queued'}`; `GET /jobs?serverId=...` reports queued/running/succeeded/failed, timestamps and error. Jobs are claimed in per-server order (no parallel jobs for one server), lease for two minutes, renew while executing, retry up to five times, and reject renewals/results after a lease expires (even before another pickup); the node persists successful destructive-job receipts so reconnects do not rerun successful work. A crashed mid-restore can still leave partially restored files; see limitations.

`GET /servers/:id/console` remains a snapshot of recent Docker logs for compatibility. The UI's live console uses WebSocket: nodes establish authenticated outbound connections and publish incremental Docker logs and CPU/RAM samples while authorized viewers are subscribed; the API checks browser sessions, Origin and console grants. Short-lived events and node leases are stored in PostgreSQL so API processes can route streams through the database. `POST .../console` `{command}` continues to use Minecraft `rcon-cli` for Minecraft Java; for other images, the agent writes one validated line to a persistent Docker stdin attachment. New containers keep stdin open. Existing containers need a configure/recreate after a backup before they can accept input. Other game software must itself read console commands from stdin; Fledge does not expose a host shell. A real Docker stdin integration check is in `agent/console_test.go`. Multi-process protocol smoke coverage exists; production load, restart-under-stream, and multi-host validation remain outstanding.

File endpoints use a *virtual absolute path* under that server's data directory, Linux `openat` + `O_NOFOLLOW` for file operations, symlinks excluded. `GET /files?path=/` returns `{path,items:[{name,path,type,size,modifiedAt}]}`; `GET/PUT /files/content?path=/...` supports editor content up to 1 MiB; streaming browser upload/download routes relay up to 1 GiB through object storage and an agent job; `POST /files/mkdir` `{path}`; `POST /files/extract` `{path}` extracts ZIP only (100 MiB total decompressed). Transfer URLs are short-lived and scoped to the user/server; agents write downloads atomically after validation. SFTP is optional per agent (`SFTP_LISTEN`) and uses per-server short-lived credentials. Logical allowances are enforced for transfer/SFTP writes; game processes can still exceed them because these are not kernel-enforced filesystem quotas.

`GET /servers/:id/backups`, `POST /servers/:id/backups` (or action `backup`) queue tar.gz of local volume uploaded to S3 via a presigned PUT; `GET /servers/:id/backups/:backupId/download` redirects to a signed GET; `DELETE /servers/:id/backups/:backupId` deletes the S3 object and metadata. Restore: `POST /servers/:targetId/actions` `{action:'restore',backupId,confirm:true}`; admin can use any completed backup; non-admins may use only a backup from a server belonging to the target's owner **and** must own that source server or have its `backups`/`manage` grant. A manage collaborator on a target cannot restore from an unrelated private source server merely by knowing a backup UUID. The agent preserves whether the target container was running, downloads to a staging directory, verifies gzip/tar checksums and safe entry types/paths, and swaps directories with Linux `renameat2(RENAME_EXCHANGE)` on supported filesystems/architectures; unsupported atomic exchange fails closed. A failed restart attempts to roll the swap back. After a successful swap the old directory is removed; retain an independent backup before restoring. For cross-node recovery, **create a new server on a healthy node first, then restore the old backup there**; configure DNS/port changes yourself. Backups are integrity-verified live tar archives—not quiesced, atomic or game-consistent snapshots—and edits by the running game can be inconsistent. Retention is configurable as documented above. Automatic stateful failover and scheduled test restores are not implemented.

`GET/POST/DELETE /servers/:id/schedules` supports `{kind:'backup'|'command',command?,intervalMinutes}` (minimum five minutes); command schedules only on Minecraft. `GET /servers/:id/backups/policy` and `PATCH .../backups/policy` read/update `{retentionDays}` (0 disables, range 0–3650), owner/manage/admin only for updates. A 15-second control-plane sweep deletes expired S3 objects and rows, never the latest successful backup or one referenced by an active restore. S3 and PostgreSQL cannot commit atomically; deletion is made retryable and should be monitored. `GET/POST/DELETE /servers/:id/collaborators` adds an **existing** customer by `{email,permissions:['view'|'console'|'files'|'backups'|'manage']}`. Owner or manage collaborator controls sharing. No invitation email.

### Agent protocol (not browser endpoints)

`POST /agent/enroll` `{nodeId,token}` returns `{credential}` exactly once. Subsequent calls send `Authorization: Bearer <credential>` and `X-Node-ID: <id>`: `POST /agent/heartbeat`, `GET /agent/jobs`, `POST /agent/jobs/:id/renew`, `POST /agent/jobs/:id/result`. Each leased job has `{id,kind,attempt,payload,server}`; completion carries `{attempt,success,result?,error?}`. Heartbeat contains version, host usage and observed container statuses. URL signatures for backup/restore are generated at pickup, valid for one hour. Do not expose this protocol to public networks without HTTPS/rate limiting.

## Verification and known gaps

The repeatable API smoke suite runs against a disposable PostgreSQL container and simulated agent HTTP/WebSocket traffic. It covers authentication and 2FA, request throttling, enrollment, two-node placement, job leasing, permissions, live console routing, and server operations. Separate API tests cover CORS, release checks, and Pterodactyl conversion. Agent tests cover SFTP, safe file operations, backup lifecycle, archive verification/restore, and console framing; an optional Docker test checks live stdin against a disposable container. In the 2026-09-25 local validation, a real Minecraft Java container booted on Docker Desktop with a WSL2 agent, accepted a console command, served a file listing and Docker resource sample, created a 108 MiB S3-compatible backup, and restored it successfully. This did not exercise Valheim, AWS S3, or a separate physical host.

The API supports PostgreSQL-backed request throttles, one-time recovery codes, admin-only Prometheus metrics, and application-code rollback when updater health checks fail. The agent gracefully stops and restarts a running container around archive creation and retains prior run state. Backups remain non-atomic archives, not game-aware snapshots. Scheduled verification validates the stored archive and extraction safety; it does not launch the game.

Unresolved operational limits: hard filesystem quotas; automatic stateful failover and live migration; game-boot restore verification; sustained multi-replica/load testing; real AWS S3 retention; separate-host recovery; native Windows services/containers; rootless agent operation; external observability and formal security review. Update rollback cannot reverse a database schema migration. The Docker socket remains root-equivalent. Recovery requires a saved recovery code, and changing lost credentials without one requires an administrator with database access. Use dedicated Linux nodes, HTTPS, a restricted agent egress/firewall policy, off-host backups, and tested restore procedures before production use.
